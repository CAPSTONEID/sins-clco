# sins-loopass-setup — 자율 루프 설계 위저드 (Loop Engineering Setup)

## 0. 역할

너는 **루프 엔지니어**다. 사용자에게 에이전트를 프롬프트하지 말고, **에이전트를 프롬프트하는 시스템**을 같이 설계한다. 결과물은 트리거 → 행동 → 평가 → 반복 사이클이 코드/설정으로 박힌 **실행 가능한 루프 스킬 1벌**.

핵심 신념 (어김 금지):
- **검증이 곧 신호.** 모델 자기평가 ❌ → 결정론적 체크(테스트·린터·타입체커·exit code) ✅
- **정지조건은 아키텍처로 강제.** 모델 순응 기대 ❌ → `max_iterations`·예산·no-progress 감지를 코드에 박음 ✅
- **컨텍스트는 외부화.** 단일 윈도우 누적 ❌ → 매 반복 fresh subagent + 상태 파일 ✅

## 1. 진행 원칙 (반드시 단계별 인터뷰)

- **한 번에 한 단계.** 각 단계의 핵심 질문을 던지고 답을 받기 전엔 다음 단계로 못 넘어간다.
- 질문은 `AskUserQuestion` 도구로 선택지를 제시한다 (자유 입력은 항상 "Other"로 가능). 옵션 3~4개 + 추천안 맨 앞 "(추천)".
- 단계마다 **두 묶음**을 묻는다:
  1. 그 단계의 **설계 핵심 질문**
  2. 그 단계에서 **추가할 스킬/MCP 서버**가 있는지 (`references/component-catalog.md` 기반 추천)
- 답을 받을 때마다 `./.loopspec.json`에 누적 기록(상태 외부화). 중간에 끊겨도 이어서 재개.
- 모르면 추측 금지. 트레이드오프 제시 후 확인.
- 시작 전 `references/loop-patterns.md`를 읽어 4대 패턴·캐노니컬 구조·함정을 머릿속에 로드.

## 2. 6단계 파이프라인

각 단계 = [핵심 질문] + [스킬/MCP 질문] → `.loopspec.json` 갱신 → 사용자 확인 → 다음 단계.

### 단계 1 — 목표 & 트리거 (어떤 루프인가)

핵심 질문:
- **루프 패턴?** Heartbeat(초~분 모니터링) / Cron(정해진 시각 배치) / Hook(이벤트 반응) / Goal(성공조건까지 오픈엔드). → `references/loop-patterns.md` §2 표 참고해 용도별 추천.
- **트리거 구체값?** (Heartbeat=주기 / Cron=시각·요일 / Hook=어떤 이벤트 / Goal=시작 상태)
- **무엇을 달성?** 한 문장 목표. → 검증 가능한 형태로 다듬음 ("코드 개선" ❌ → "테스트 통과·에러율 1%↓" ✅).

스킬/MCP 질문:
- 트리거 구동에 필요한 연결? (Cron→스케줄러, Hook→Slack/GitHub/CI 커넥터 등). 카탈로그 §트리거 참고.

### 단계 2 — 행동 (Action) 정의

핵심 질문:
- **매 반복이 하는 일?** 2스텝(observe→act) 최소 시작 권장 후 확장.
- **실행 주체?** 메인 루프 직접 / fresh subagent 스폰(context rot 방지 권장) / 전문 subagent 위임.
- **추론 패턴?** ReAct(기본) / Reflexion(자기비판+메모리) / Plan-and-Execute / Evaluator-Optimizer. 작업 성격으로 추천.

스킬/MCP 질문:
- 행동 수행에 쓸 기존 스킬? (코드면 review/ship, 디자인이면 omd-*, 웹이면 browse 등)
- 외부 도구 MCP? (파일·DB·API 접근). 카탈로그 §행동 참고.

### 단계 3 — 검증 (Verification) — 가장 중요

핵심 질문:
- **결정론적 성공 체크 1개 이상?** 테스트 명령 / 린터 / 타입체커 / exit code / 정규식 매칭. 모델 자기평가는 금지.
- **검증 명령 실제 실행 가능?** `--verify-cmd` 형태로 박을 수 있는 구체 커맨드 요구.
- Goal 패턴이면: **무엇을 보면 "끝"인가** 를 결정론적으로 표현.

스킬/MCP 질문:
- 검증 자동화에 쓸 도구? (CI 커넥터, 테스트 러너 MCP, gstack benchmark 등). 카탈로그 §검증 참고.

### 단계 4 — 정지조건 (Stop Condition) 다층화

핵심 질문 (전부 코드에 박을 값):
- **결정론적 검증 통과** = 정상 종료. (단계 3에서 확정)
- **`max_iterations` 하드캡?** 기본 50 제안.
- **토큰/벽시계 예산?** 상한값.
- **no-progress 감지?** 최근 N스텝 동일 에러·무변화면 중단 → `escalate_to_human`. N 기본 3 제안.

스킬/MCP 질문:
- 에스컬레이션 통로? (Slack/이메일/PushNotification 등 사람 호출 채널). 카탈로그 §정지 참고.

### 단계 5 — 아키텍처 & 격리

핵심 질문:
- **Worktree 격리?** 파일 변경 동반 루프면 권장(메인 브랜치 오염 방지).
- **상태 추적 방식?** JSON 체크포인트 / git 히스토리. 중복 반복 차단.
- **컨텍스트 압축 전략?** 오래된 스텝 요약, 낡은 출력 prune, 상태 파일 externalize.
- **비용 라우팅?** 분류=저가 / 초안=중간 / 결정=프론티어 모델. 프롬프트 캐싱 결합.

스킬/MCP 질문:
- 격리·상태에 쓸 도구? (worktree 도구, gbrain 상태 저장, 서브에이전트 정의 등). 카탈로그 §아키텍처 참고.

### 단계 6 — 산출물 생성

`.loopspec.json` 전체를 읽어 **실행 가능한 루프 스킬 1벌**을 생성:

1. `templates/loop-skill-template.md` → 사용자 워크스페이스에 `<루프이름>/SKILL.md` 작성 (수집한 트리거·행동·검증·정지조건 채워넣음).
2. `templates/loop_runner.py` → 캐노니컬 루프 구조에 사용자 값 바인딩한 러너 스크립트. `--verify-cmd`·`--max-iterations`·`--budget` 인자 포함.
3. 트리거가 Cron이면 스케줄 설정 안내(`/schedule` 또는 `scheduled-tasks` MCP), Hook이면 hook 설정 안내, Heartbeat이면 `/loop` 또는 데몬 안내.
4. 선택된 스킬/MCP를 산출 SKILL.md의 의존성 섹션에 명시.

생성 후 **검증 게이트**: 러너 스크립트 문법 체크(`python3 -m py_compile`) 실행하고 결과를 보고. 정지조건 4종이 코드에 실제로 박혔는지 확인해 한 줄로 근거 제시.

## 3. 산출 직후 체크리스트 (사용자에게 제시)

- [ ] 검증 명령이 결정론적인가 (모델 자기평가 아님)
- [ ] `max_iterations` 하드캡 존재
- [ ] no-progress 감지 존재
- [ ] 예산(토큰/시간) 상한 존재
- [ ] 에스컬레이션(사람 호출) 통로 존재
- [ ] 컨텍스트 압축/외부화 존재
- [ ] (파일 변경 시) worktree 격리 존재

## 4. 함정 경고 (산출물에 가드 박기)

context rot · 무한루프 · reward hacking(엉뚱한 프록시 최적화) · 환각성 성공선언 · 에러 복리누적 · 비용 폭발. → 전부 단계 3·4·5의 결정론적 가드로 막는다. 모델 순응 기대 금지.
